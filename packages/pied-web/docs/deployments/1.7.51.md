# Deployment 1.7.51, 2026-09-16

Seventeen releases were prepared in one session, from the *Refactoring UI* audit
recorded in the parent notebook, and installed together as 1.7.51: two
housekeeping steps with no visual effect (1.7.35 flattening the studio
stylesheet, 1.7.36 adding the token layer), eleven targeted corrections, three
system passes over type, spacing and colour, and the font leaving the
stylesheet. Only six files carry all of it — `index.php`, `ux.css`, `ux.js`,
the theme stylesheet and two new font files — because everything else is
generated into `style.css`.

## Preflight

Read-only comparison of the installed payload against the 1.7.34 manifest: 38
of 38 tracked files identical, none missing, no foreign file, every file mode
644 — 36 plugin files and 2 theme files. Production was a clean 1.7.34 with no
drift.

Backups outside the web root, before any write:

- `~/nextsnapmail-pied-web-backups/pied-web-ux-1.7.34-20260916T054223Z`
  (36 files, 520 K, `index.php` SHA-256 `4a851121…`)
- `~/nextsnapmail-pied-web-backups/PiedWeb-theme-1.7.34-20260916T054223Z`
  (2 files, 500 K, `style.css` SHA-256 `5ccaa91c…`)

Served state before the write, read in an authenticated session: plugin bundle
key `21e817499a3d1c91bd4aaac93e4f86f0`, theme marker `PiedWeb@nextcloud`, one
font face covering `U+0-10FFFF` — the embedded one — and no `--pw-*` scale
token resolving.

The one new risk in this release was checked before installing anything. The
stylesheet now asks for its font with a relative `url()`, and
`RainLoop\Actions\Themes::compileCss()` rewrites that to `\OC::$WEBROOT . '/'`
for a `@nextcloud` theme; line 143 of the installed copy on this host confirms
the rule. `/themes/PiedWeb/snappymail/preview.png` was fetched over the web
first and answered 200 with the installed file's exact size, so the directory
the rewritten URL points at is served.

## Installation

Files were staged privately in `~/.pw-stage-1.7.51` (mode 700), their bytes
compared with the 1.7.51 manifest — all six equal — and the server's own
`php -l` accepted the new `index.php` before any write.

Installation order put every asset ahead of the file that announces the
version, and the two new font files ahead of the stylesheet that names them, so
the theme never referenced a file that did not exist yet:

1. `pied-web-ui-latin.woff2`, `pied-web-ui-latin-ext.woff2`
2. `themes/PiedWeb/snappymail/style.css`
3. `ux.css`, `ux.js`
4. `index.php`

Installed hashes equal the manifest across all 40 payload files, with no drift,
nothing missing, no foreign file and mode 644 throughout — 36 plugin files and
4 theme files. The staging directory was removed.

Workers were recycled with `pkill -u robindfr lsphp` (11 workers before, 0
after) followed by a warm-up request, `status.php` 200 in 0.68 s. The served
plugin bundle key changed from `21e817499a3d1c91bd4aaac93e4f86f0` to
`1ef81c5b50a93ce155a6bdab76d60589`, which remains the only reliable proof of
web activation with `opcache.validate_timestamps=0`. As since 1.7.30, the
compiled stylesheet is keyed on that hash, so the version bump is again what
makes the changed stylesheet reachable.

## Boundaries

The composer was deliberately not opened on production. Its action hierarchy and
the accessible name on the discard control are covered end to end by
`test-composer-actions.js` against the native markup of SnappyMail 2.38.2, and
opening the real composer risks offering to save a draft in a real mailbox.

No message in the visible Inbox was followed, so the amber edge accent from
1.7.39 was not observed on production; it is covered by two fixture cases and by
the no-JavaScript fallback fixture.

The empty-state work was not observed on production either: it needs an empty
folder or a search with no result, and neither was provoked in a real mailbox.

The Latin-Extended font file was confirmed to be served and to stay unfetched,
but no message requiring it was displayed, so its rendering was checked only in
the fixture.

## Observed, not caused by this release

The Inbox folder label truncates to "Boîte de réception…" in the 248 px rail.
Measured on production, the row overflows its content box by 20 px; restoring
the 1.7.34 geometry for that row alone — 36 px end padding — makes it 24 px, and
restoring the older 13 px text as well still leaves 14 px. The cause is
SnappyMail's own `span.flag-icon` inside the Inbox anchor, 26 px wide, on top of
the folder icon and the 32 px reserved for the unread badge. This release made
the overflow smaller; it did not create it and does not fix it.

The quotation toggle in the reader still renders the engine's own "▶" text
glyph. It is a fourth native default of the kind 1.7.47 replaced, and it was not
part of that release.

## Rollback

This release adds two files and changes four:

- copy `~/nextsnapmail-pied-web-backups/pied-web-ux-1.7.34-20260916T054223Z/`
  `{index.php,ux.css,ux.js}` over the installed plugin files,
- copy `~/nextsnapmail-pied-web-backups/PiedWeb-theme-1.7.34-20260916T054223Z/`
  `snappymail/style.css` over the installed theme stylesheet,
- delete the installed `pied-web-ui-latin.woff2` and `pied-web-ui-latin-ext.woff2`,

then recycle with `pkill -u robindfr lsphp` and a warm-up request and confirm the
bundle key returns to `21e817499a3d1c91bd4aaac93e4f86f0`. Deleting the two font
files is safe in either order relative to the stylesheet, because the 1.7.34
stylesheet carries its own font and never asks for them; leaving them in place
would simply mean the theme directory no longer matches the 1.7.34 manifest. The
1.7.34 fingerprints are in this repository's git history. This release writes no
data and no configuration.
