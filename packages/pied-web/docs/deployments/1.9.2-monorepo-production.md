# Deployment: monorepo release 1.9.2

Pied Web **1.9.2** was installed on the n0c production instance on 2026-09-19
from the canonical `PiedWeb/NextSnapMail` monorepo. This activation introduces
the account-safe Feed released in 1.9.0 and the compact reorderable folder rail
released in 1.9.2. It does not replace the NextSnapMail application or change
mail, account, calendar, Sieve or scheduler configuration.

## Source and preflight

- monorepo baseline: `61800e0d59939261c2576cd3ff0044609f09cad9`;
- product archive: `nextsnapmail-pied-web-1.9.2.tar.gz`;
- archive SHA-256: `a22ac18a0e04b60430d3cbb21e111b222f0dc87a6c7022fa3ef9488a7dd0ebee`;
- production compatibility: Nextcloud 34.0.4, NextSnapMail 0.1.11,
  embedded SnappyMail 2.38.2;
- initial state: plugin 1.8.19, Nextcloud outside maintenance mode and no
  database upgrade pending.

The complete monorepo test suite passed locally: core account-counter tests,
product verification, PHP/JavaScript syntax, reproducible theme build and all
mocked native integration suites. The archive checksum matched after transfer.
The host has no `node` binary, so the staged `tools/verify.py` could not repeat
its JavaScript syntax phase there; server PHP lint, payload checks and the full
local suite cover that boundary.

## Web runtime activation

An authenticated request initially still reported Pied Web **1.8.19**, although
the installed files matched 1.9.2. LiteSpeed had cached `index.php`,
`Conversation.php`, `UnreadDrafts.php` and `UnreadOrder.php` with timestamp
validation disabled.

The targeted `pied-web-runtime-maintenance-v7` helper invalidated the ten fixed
PHP paths of `pied-web-ux`; it accepted no caller-provided path. Every invalidation
returned success. A separate authenticated request then reported **1.9.2**. The
cleanup restored `application.ini` byte-for-byte, removed the temporary plugin
and detected no concurrent configuration change. Its private temporary directory,
including the configuration copy, was deleted afterwards.

With no composer open, the authenticated Mail page was reloaded. It served plugin
bundle key `d9bcd4590a6a708626e6e731b4d59c46`; the Pied Web theme and font loaded, the
two Feed links were present, the global Feed rendered 86 account-scoped rows, and
the compact rail mounted ten named keyboard-reachable controls. No visible error
state was present. No message was opened, sent, moved, deleted, flagged or marked
read during this verification.

The post-deployment instance audit matched **84 of 84** tracked files, with no
mismatch. The Calendar patch, `.htaccess` protections, 30-day Mail HTTP cache and
five-domain image CSP remained unchanged and conforming.

## Rollback

Restore the changed 1.8.19 files from the two backups, remove only the four files
that did not exist in 1.8.19 (`Feed.php`, `FolderOrder.php`, `feed.js` and
`folder-rail.js`), and install the backed-up `index.php` last. Restore
`PiedWeb-theme-1.8.19-20260919T194452Z/snappymail/style.css` to the active theme.
Then run the current targeted Web-runtime procedure, verify a separate
authenticated request reports 1.8.19, reload with no composer open and run the
1.8.19 manifest check. The rollback does not touch mail or account settings.
