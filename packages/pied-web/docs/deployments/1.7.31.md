# Deployment 1.7.31, 2026-09-15

Performance work following the request-level measurement recorded in
[`docs/perf-2026-09-15.md`](../../../docs/perf-2026-09-15.md) of the instance
notebook. The reader conversation stack drove its own search from the browser:
opening a fourteen-message thread issued 31 backend requests and about 4,7 s of
activity, and repeated the whole scan every 60 seconds while the message stayed
open. Each request paid a full Nextcloud bootstrap and a fresh IMAP connect and
login, because `RainLoop\Actions::initMailClientConnection()` reconnects on
every request. The walk now runs in a new `PiedWebConversation` JSON hook on a
single authenticated connection.

The read-only comparison matched the installed plugin byte for byte against the

## Stylesheet

The desktop attachment controls that were pending in the working tree went out
with this release, on the owner's decision: a single attachment no longer shows
SnappyMail's settings cog, two or more show the native selection controls and
“Download as zip”, and the tiles get 18 px before the lower divider. Production
backup of the previous theme directory:
`~/nextsnapmail-pied-web-backups/PiedWeb-theme-1.7.25-20260915T1950Z`
(`style.css` SHA-256 `0191639e5858db1a861aec0273135b4d130383d72a9d9661dc00bee53b97bdf8`).

Deploying the stylesheet under the unchanged 1.7.30 plugin version was not
enough: the served CSS still contained the 1.7.25 rules. `ServiceActions` caches
the compiled stylesheet under `/CssCache/<Plugins()->Hash()>/<theme>/<APP_VERSION>/`,
and that hash does not depend on the theme file. Version 1.7.31 changes the hash;
the served stylesheet then carried all eight `attachmentsControls` rules and the
`14px 0 18px` padding, verified by fetching the live CSS endpoint.

## Withdrawn intermediate versions

Three payloads were installed on production and replaced during this session.
None was tagged or published.

- **1.7.26** — the inline-image queue also watched the `src` attribute, so the
  mutation observer saw the queue's own write and re-held each image the instant
  it was released. Inline images stayed blank.
- **1.7.27** — the queue waited for `load` or `error` before releasing the next
  slot. SnappyMail marks these images `loading="lazy"`, so an image in a hidden
  message body fires neither and the queue stalled permanently once the reader
  moved on. 1.7.28 added a timer, 1.7.29 removed the queue entirely.
- **1.7.30** — plugin-only intermediate step, superseded within the same session
  once the owner decided to ship the pending stylesheet as well.
- **1.7.29** — the conversation scan called the new endpoint through
  `rl.app.Remote.post`, which serves native message actions. Plugin hooks answer
  through `rl.pluginRemoteRequest`, as the unread-drafts reminder already did.
  Every scan rejected and the reader showed “Conversation incomplète”. Caught by
  the authenticated browser check, not by the endpoint tests, because the tests
  call the plugin method directly.

## Engine note worth keeping

`RainLoop\Plugins\Manager::Hash()` builds the served plugin bundle key from
`APP_VERSION`, each plugin's `class@VERSION`, and the **script file names**. File
content is not part of it, and the compiled bundle is stored in the SnappyMail
cache under that key. **Changing a plugin script without bumping the plugin
version leaves the old bundle being served**, with no visible sign. Every payload
change needs a version bump, not only for the record.

`~/.lsphp_restart.txt` did not recycle the workers on this host: they were still
six hours old after touching it, and OPcache kept the previous `index.php` with
`opcache.validate_timestamps=0`. `pkill -u robindfr lsphp` followed by a warm-up
request was used instead, as in the 12 September report, and was confirmed by
process age and by the served bundle hash changing.
